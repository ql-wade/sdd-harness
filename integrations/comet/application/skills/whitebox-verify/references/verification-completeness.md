# 验证完备性纪律（v2.1 · 2026-08-10 实战教训沉淀）

> **来源**：一次全量验证的 4 个真实漏判（详见文末 few-shot）——"入口在"当"闭环通"、沿用旧 verdict、未验证项在关闭后才登记、8 维只跑 happy path。本文件把这些教训变成可执行规范，防止复发。

当前职责：只审查作者交付的需求/测试覆盖、执行已批准流程和独立取证。以下覆盖矩阵与探针清单用于审查充分性与已知契约差异诊断；缺设计/测试/业务期望交回 test-authoring，不在验收时补写或修改。Slice 的 RED/GREEN/回归由作者交付版本与测试，验收者独立核验。

## 0. 总则

**"验证通过"必须是一个可被否证的结论，不是工作量清单。** 每条 PASS 都要能回答："什么证据能否定它？如果这段代码被删了，我的验证会发现吗？"

验证产出按**证据强度分级**，低一级的证据不得支撑高一级的结论：

| 级别 | 证据 | 能支撑的结论 |
|---|---|---|
| L1 | 代码阅读 / grep 到端点 / 单测存在 | "实现存在"（**入口在**） |
| L2 | curl/wire（HTTP/SSE 200 + 响应字段） | "链路通"（**部分闭环**） |
| L3 | 浏览器交互触发 + wire + DB/对象存储 readback + 截图（同一事件） | "功能闭环"（**闭环通**） |
| L4 | 双重证据一致性：日志/DB 时间戳与截图来自同一次调用 | "可复现闭环" |

### 声称侧反查表

**任何成功声称先反查本表，再落报告。**

| 声称 | 最低证据 | 不充分证据 |
|---|---|---|
| "闭环通" | L3 四件套（浏览器交互+wire+DB readback+截图）来自同一事件 | 截图存在 / 单测存在 |
| "bug 已修复" | 图谱全边重跑 + 回归有效性证明（debug-workflow.md#修复后回归有效性） | tsc + vitest 全绿 |
| "环境限制" | 独立证据证明不可达（连通性探测/服务状态/依赖清单） | 单次 500 |
| "入口在" | L1：代码阅读定位到 UI 元素与后端端点 | 凭记忆或旧截图 |
| "8 维已覆盖" | 逐维度 VERDICT 行 + 各自证据引用 | 只跑了 A 维 happy path |
| "无越权" | E 维探针实际执行（跨用户/跨租户/无 token 各一次）+ 响应码断言 | 只测了本人正常路径 200 |
| "性能达标" | 日志时间戳 delta / SQL 计数实测值（G 维证据） | "感觉不卡" |
| "该功能不存在" | 当前代码 L1 阅读证实 + 仓库检索零命中 | 上次运行的印象 |

## 1. 两级动词规范（铁律 6）

**禁止用同一个动词表达不同证据强度。** 报告/issue 评论/ledger 中必须强制使用三态动词：

- **入口在** = 只确认了 UI 元素/后端端点存在（L1）。不得与"可用"混用。
- **闭环通** = 浏览器交互触发 → wire → DB readback → 截图全部到位（L3/L4）。才能标 ✅。
- **未验证** = 没跑或只看到入口，诚实标注，等待验证或登记跟踪。

**判定规则**：
- 看到按钮 + grep 到端点 → 只能写"**入口在**"，**不能标 ✅**。
- 键盘/点击交互没真正触发 API 调用（无对应 network request）→ 视为"入口在/未验证"，不是闭环。
- 上传附件只确认按钮存在、没完成上传→回读 → "入口在"，不能判 #049 通过。

## 2. 逐 TC 8 维最低门槛

每条**核心用例**（源表"核心"=是）至少覆盖 **A（功能性）+ B（UI 渲染）+ C（UX/错误态）+ E（安全/权限）** 四维；跨服务/数据/性能/并发用例补齐 D/F/G/H。缺一维的用例**不允许标 ✅**，只能标 🟡（部分）并在 ledger 注明缺哪维。

**最小可接受证据组合（核心用例）**：
```
A: 真实请求 → 期望 HTTP + body 字段断言
B: 页面渲染 + 无 console error + 截图
C: 触发错误/空态 → 非白屏错误卡片（截图）
E: 越权/无 token → 401/404（curl）
```
任一条缺失 → 该用例降级为 🟡，记录"缺 B/C/E 维度证据"。

## 3. 旧 verdict 一律重推导（铁律 7）

**issue body / 历史 checklist / 上次运行记录中的 verdict 只当线索，不当前提。** 每次运行必须对目标用例重新核对当前代码 + 浏览器 + wire。

- 反模式：issue 07-24 标 ❌，我归类 roadmap 没重新查 → 实际已建（重命名/重新生成/复制/快捷输入/发起任务 5 项全翻新）。
- 规则：对每条待判用例，先问"当前代码/UI 里它到底在不在、通不通"，再写 verdict。历史 verdict 只用于对比 delta，不用于直接沿用。

## 4. 关闭前残留登记铁律（铁律 8）

**关闭任何 [验证] checklist / 范围类 issue 前，所有未完成/未验证项必须已经链接到带 owner 的跟踪 feature issue。** 顺序不可逆：**先登记，后关闭。**

- 正例：#349（任务中心 11 DEFERRED 承接 #171）、#407（chat 未建 feature 承接 #158）。
- 反例（本次）：#158 关闭后才补 #407 —— 残留项在关闭瞬间"丢失"，要靠用户发现。
- 关闭评论必须包含：剩余项清单 + 每项指向的跟踪 issue + "完成一项回写 verdict 升级"的闭环声明。

## 5. 完成偏差对抗清单（收尾必跑）

验证/报告收尾前，逐条自问并记录答案：

1. **什么证据能否定我标的每个 ✅？**（能否定 → 该 ✅ 不成立）
2. **8 维里我实际跑了几维？** 核心用例 C/E 缺了没有？缺的诚实降级。
3. **我沿用/假设了哪些"延后/roadmap/待确认"分类？** 分类本身验证过吗？还是我编的？
4. **有哪条用例我只看到了入口？** 标成"入口在"了吗，还是悄悄写成了通过？
5. **关闭动作是否跑在残留登记前面了？** 如果先关了，立即建跟踪 issue 并回链。
6. **时间压力下我砍掉了哪部分验证？** 砍掉的是否正好是难验证的（E 安全/H 并发）？

> 出现任何"我当时以为""可能没问题""先这样" → 停下来，回到对应铁律。

## 7. few-shot 正反例（本次实战提炼）

### FS-1 两级动词
- ❌ 反例：`TC-PA2-041 重命名` → 看到重命名按钮 + grep `PATCH /session/rename` → 标 ✅。**实际键盘交互没触发 rename API**（focus 问题），闭环未验证。
- ✅ 正例：点重命名 → 输入新名 → 观察 network 出现 `PATCH /session/rename` 200 → DB `runtime_session_registry.title` 回读为新值 → 截图 → 标 ✅（闭环通）。

### FS-2 旧 verdict 重推导
- ❌ 反例：issue 07-24 标 #054 重新生成 ❌，直接归类 roadmap 未在浏览器核实 → 实际 UI 已有"重新生成"按钮。
- ✅ 正例：对 #054 重新在浏览器看回复操作区 → 有"重新生成"+"复制"按钮 → 标 ✅（入口→闭环确认后再定）。

### FS-3 关闭前残留登记
- ❌ 反例：关 #158 时 17 项未建 feature 无跟踪 → 用户发现后补 #407 → 关闭瞬间残留"丢失"。
- ✅ 正例：关闭前先建 #407 列全残留项（含 owner/验收）→ 关闭评论回链 #407 → 残留不丢。

### FS-4 8 维只跑 happy path
- ❌ 反例：只验证"发送→收到回复"（A happy path）就声称 chat 领域通过 → 漏掉 E 越权、C 错误态、F DB readback。
- ✅ 正例：核心用例强制 A+B+C+E，缺维降级 🟡 并注明，不虚标。

### FS-5 环境问题 vs 代码 bug 的诚实标注
- ❌ 反例：`/api/admin/memory/entities` 500 直接当"通过"或"bug"。
- ✅ 正例：确认为 mem0 server 未在 :8000（环境配置）→ 页面有正确错误态 → 记为"环境限制"，不虚标通过也不误报 bug，明确区分。

## 8. 验证者隔离与结果态优先

### 8.1 验证者/生成者隔离：verdict 只从原始证据推导

**规则**：验证者（负责判定 verdict 的运行/代理）不得把被验证方（实现方、被测变更作者）的自述——总结、承诺、"已修复"声明、自产测试报告——当作 verdict 证据。verdict 只从**原始证据**推导：独立执行的命令输出、wire 捕获、DB 读回、日志原文、浏览器观察。

- 与铁律 7（旧 verdict 一律重推导）同根：**self-authored artifacts 不可信**。journey 校验器同样明确：`STRUCTURE_PASS` 只证明结构自洽，"不证明命令真实执行过、不证明自产工件可信"（见 `journey-contract.md` validator 一节）。
- 被验证方自述只能当**线索**（提示去取哪类证据），不能当**证据**。
- 实操：报告里每条 PASS 的 evidence-ref 必须指向验证者自己（或可独立重放的工具）产生的工件；出现"实现方称 / 作者说明 / PR 描述称"且无独立证据 → 该条至少降为 UNVERIFIED。

### 8.2 PASS verdict 抽样审计纪律

**动机**：门禁类校验（validator / lint）查的是结构性失败（假阳性），对**假阴性不可见**——一条错误的 PASS 不会让任何工具报错。抽查是对冲假阴性的唯一手段。

**纪律**：
- 对已判 PASS 的结论抽样深审：抽中项必须能回答"什么证据能否定它"（衔接 §5 对抗清单第 1 条），并至少**重放一条底层证据**（重跑命令 / 重读 DB / 重看截图对应现场）。
- 抽样发现错判 → 该批次同类 PASS 全部降级重验，并把教训补成一条新的反查规则（进声称侧反查表或对抗清单）。
- 抽样审计本身留痕：抽了哪些项、重放了哪些证据、结果如何，供下轮审计对比。

### 8.3 结果态优先（判终局，不判过程）

- **Slice TDD 双门禁**：终局断言必须同时过 **fail-to-pass**（实现前亲见 RED、实现后 GREEN——证明测试真的在测这个变更）与 **pass-to-pass**（变更前后无关的既有断言仍绿——证明没有破坏别处）。只看 fail-to-pass 漏回归，只看 pass-to-pass 漏功能缺失。
- **Journey 查终端系统状态而非过程输出**：判定点取**系统终局状态**（DB 读回、队列消费位点、下游系统内的观察），不取过程性输出（日志行、中间事件、"已触发"回执）。过程输出只能定位断点，不能闭合 Journey。
- **保留 Unknown 出口，不强迫二值**：证据不足以判 PASS/FAIL 时，判定保留 Unknown / UNVERIFIED 态，写明阻塞原因与所需证据；禁止为了"闭合"把不确定强行记成 PASS 或 FAIL。Journey 契约同语义：Unknown values are explicit blockers, never shorthand。

## 置信度与假阳性控制

每条 finding 必须附置信度标注：

| 置信度 | 判定标准 | 报告动作 |
|---|---|---|
| **高** | 受控前提下独立复现 ≥2 次 + 反向证据排除环境因素（换浏览器/换账号/换数据后仍存在） | 直接计缺陷 |
| **中** | 受控前提下复现 1 次 | 计缺陷，注明"复现 1 次" |
| **低** | 单次观察 | 标 **待复核**，入残留项（衔接铁律 8 残留登记），不计已确认缺陷 |

**明确排除项**：环境不可用（服务未起、依赖缺失、网络不可达）不构成缺陷——记 **环境限制**（衔接 FS-5：不虚标通过、不误报 bug），且**不得静默丢弃**，必须列入报告并附独立证据。

**越权/注入类 finding**：必须附可复现 curl 原文（完整 header/body + 期望 vs 实际响应），使他人可粘贴执行复现。

## E 维攻击面五类清单

调试模式 E 维（安全/权限）逐类过一遍，每类至少一个探针：

| # | 攻击面 | 覆盖 |
|---|---|---|
| 1 | 输入校验注入 | SQL 注入 / 命令注入 / 路径穿越 / 模板注入 / NoSQL 注入 |
| 2 | 越权 | 水平越权 / 垂直越权 / 跨租户隔离 / 会话 token 边界（过期·伪造·他人 token） |
| 3 | 密钥与敏感数据 | 日志 / console / `__wbvLog` 捕获体中的 Authorization、token、PII 泄漏 |
| 4 | 反序列化与动态执行 | 不受信反序列化入口 / eval·Function·动态 require 类执行 |
| 5 | 数据暴露 | 响应体 PII / 调试信息 / 错误栈外泄 |

边界声明（不变）：E 维是**功能级越权验证**（本功能是否漏拦了不该放行的人），是功能正确性的一部分；系统级安全审计（XSS/CSRF 扫描等专项）仍在 OUT OF SCOPE，两者不冲突。
