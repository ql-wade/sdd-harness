# 验证完备性纪律（v2.1 · 2026-08-10 实战教训沉淀）

> **来源**：一次全量验证的 4 个真实漏判（详见文末 few-shot）——"入口在"当"闭环通"、沿用旧 verdict、未验证项在关闭后才登记、8 维只跑 happy path。本文件把这些教训变成可执行规范，防止复发。

## 0. 总则

**"验证通过"必须是一个可被否证的结论，不是工作量清单。** 每条 PASS 都要能回答："什么证据能否定它？如果这段代码被删了，我的验证会发现吗？"

验证产出按**证据强度分级**，低一级的证据不得支撑高一级的结论：

| 级别 | 证据 | 能支撑的结论 |
|---|---|---|
| L1 | 代码阅读 / grep 到端点 / 单测存在 | "实现存在"（**入口在**） |
| L2 | curl/wire（HTTP/SSE 200 + 响应字段） | "链路通"（**部分闭环**） |
| L3 | 浏览器交互触发 + wire + DB/对象存储 readback + 截图（同一事件） | "功能闭环"（**闭环通**） |
| L4 | 双重证据一致性：日志/DB 时间戳与截图来自同一次调用 | "可复现闭环" |

## 1. 两级动词规范（铁律 #20）

**禁止用同一个动词表达不同证据强度。** 报告/issue 评论/ledger 中必须强制使用三态动词：

- **入口在** = 只确认了 UI 元素/后端端点存在（L1）。不得与"可用"混用。
- **闭环通** = 浏览器交互触发 → wire → DB readback → 截图全部到位（L3/L4）。才能标 ✅。
- **未验证** = 没跑或只看到入口，诚实标注，等待验证或登记跟踪。

**判定规则**：
- 看到按钮 + grep 到端点 → 只能写"**入口在**"，**不能标 ✅**。
- 键盘/点击交互没真正触发 API 调用（无对应 network request）→ 视为"入口在/未验证"，不是闭环。
- 上传附件只确认按钮存在、没完成上传→回读 → "入口在"，不能判 #049 通过。

## 2. 逐 TC 8 维最低门槛

每条**核心用例**（源表"核心"=是）至少覆盖 **A（功能性）+ B（UI 渲染）+ C（UX/错误态）+ E（安全/权限）** 四维；跨服务/数据/性能/并发用例补齐 D/F/G/H。缺一维的用例**不允许标 ✅**，只能标 🟡（部分）并在 ledger 注明缺哪维。

**最小可接受证据组合（核心用例）**：
```
A: 真实请求 → 期望 HTTP + body 字段断言
B: 页面渲染 + 无 console error + 截图
C: 触发错误/空态 → 非白屏错误卡片（截图）
E: 越权/无 token → 401/404（curl）
```
任一条缺失 → 该用例降级为 🟡，记录"缺 B/C/E 维度证据"。

## 3. 旧 verdict 一律重推导（铁律 #21）

**issue body / 历史 checklist / 上次运行记录中的 verdict 只当线索，不当前提。** 每次运行必须对目标用例重新核对当前代码 + 浏览器 + wire。

- 反模式：issue 07-24 标 ❌，我归类 roadmap 没重新查 → 实际已建（重命名/重新生成/复制/快捷输入/发起任务 5 项全翻新）。
- 规则：对每条待判用例，先问"当前代码/UI 里它到底在不在、通不通"，再写 verdict。历史 verdict 只用于对比 delta，不用于直接沿用。

## 4. 关闭前残留登记铁律（铁律 #22）

**关闭任何 [验证] checklist / 范围类 issue 前，所有未完成/未验证项必须已经链接到带 owner 的跟踪 feature issue。** 顺序不可逆：**先登记，后关闭。**

- 正例：#349（任务中心 11 DEFERRED 承接 #171）、#407（chat 未建 feature 承接 #158）。
- 反例（本次）：#158 关闭后才补 #407 —— 残留项在关闭瞬间"丢失"，要靠用户发现。
- 关闭评论必须包含：剩余项清单 + 每项指向的跟踪 issue + "完成一项回写 verdict 升级"的闭环声明。

## 5. 完成偏差对抗清单（收尾必跑）

验证/报告收尾前，逐条自问并记录答案：

1. **什么证据能否定我标的每个 ✅？**（能否定 → 该 ✅ 不成立）
2. **8 维里我实际跑了几维？** 核心用例 C/E 缺了没有？缺的诚实降级。
3. **我沿用/假设了哪些"延后/roadmap/待确认"分类？** 分类本身验证过吗？还是我编的？
4. **有哪条用例我只看到了入口？** 标成"入口在"了吗，还是悄悄写成了通过？
5. **关闭动作是否跑在残留登记前面了？** 如果先关了，立即建跟踪 issue 并回链。
6. **时间压力下我砍掉了哪部分验证？** 砍掉的是否正好是难验证的（E 安全/H 并发）？

> 出现任何"我当时以为""可能没问题""先这样" → 停下来，回到对应铁律。

## 6. TC 矩阵可执行化模板

把领域 TC 列表转成可勾选 ledger（每领域一份），✅ 机械判定：

```markdown
| TC | 用例 | 核心 | 状态 | A 功能 | B 渲染 | C 错误 | E 安全 | 证据(截图/wire/DB) | 动词 |
|---|---|---|---|---|---|---|---|---|---|
| TC-PA2-041 | 重命名会话 | 否 | ✅ | PATCH /rename 200 | DOM | n/a | 401 | 13-session.png + DB title 回读 | 闭环通 |
| TC-PA2-073 | 移动端 | 否 | 🟡 | /m-chat 200 | 375×812 截图 | n/a | n/a | 缺真机 | 入口在 |
```
- ✅ 仅当：A/B/C/E 达最小门槛 + 证据字段非空 + 动词=闭环通。
- 🟡 仅当：有部分证据但缺维度，注明缺哪维。
- ❌ 仅当：当前代码确认没有该能力（L1 阅读证实），且注明"功能未建（roadmap 缺口）"。

## 7. few-shot 正反例（本次实战提炼）

### FS-1 两级动词
- ❌ 反例：`TC-PA2-041 重命名` → 看到重命名按钮 + grep `PATCH /session/rename` → 标 ✅。**实际键盘交互没触发 rename API**（focus 问题），闭环未验证。
- ✅ 正例：点重命名 → 输入新名 → 观察 network 出现 `PATCH /session/rename` 200 → DB `runtime_session_registry.title` 回读为新值 → 截图 → 标 ✅（闭环通）。

### FS-2 旧 verdict 重推导
- ❌ 反例：issue 07-24 标 #054 重新生成 ❌，直接归类 roadmap 未在浏览器核实 → 实际 UI 已有"重新生成"按钮。
- ✅ 正例：对 #054 重新在浏览器看回复操作区 → 有"重新生成"+"复制"按钮 → 标 ✅（入口→闭环确认后再定）。

### FS-3 关闭前残留登记
- ❌ 反例：关 #158 时 17 项未建 feature 无跟踪 → 用户发现后补 #407 → 关闭瞬间残留"丢失"。
- ✅ 正例：关闭前先建 #407 列全残留项（含 owner/验收）→ 关闭评论回链 #407 → 残留不丢。

### FS-4 8 维只跑 happy path
- ❌ 反例：只验证"发送→收到回复"（A happy path）就声称 chat 领域通过 → 漏掉 E 越权、C 错误态、F DB readback。
- ✅ 正例：核心用例强制 A+B+C+E，缺维降级 🟡 并注明，不虚标。

### FS-5 环境问题 vs 代码 bug 的诚实标注
- ❌ 反例：`/api/admin/memory/entities` 500 直接当"通过"或"bug"。
- ✅ 正例：确认为 mem0 server 未在 :8000（环境配置）→ 页面有正确错误态 → 记为"环境限制"，不虚标通过也不误报 bug，明确区分。
