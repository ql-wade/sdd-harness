## Reusable native capability and its boundary

The actual0.163 help supports `codex exec --json --ephemeral`, `app-server` stdio and schema tooling, and `exec-server --listen stdio://`. These were help/parser observations only. The installed schema confirms `thread/start` and `turn/start` accept `environments`; an empty list explicitly disables environment access. `dynamicTools` and `item/tool/call` are present, as are threadId/turnId/callId fields. This makes a bounded host-CLI/in-process tool-client design plausible without a new model gateway.

However, the actual `EnvironmentAddParams` requires environmentId and execServerUrl, describes WebSocket connection behavior, and has no Docker-attach/stdio command binding. Existing exec-server stdio support therefore does not establish a ready app-server-to-I02 connection. `multiAgentMode=explicitRequestOnly` is documented in the schema as instructions; it is not a hard denial of nested dispatch. Disabling environments is likewise not proof that inherited plugins, MCPs, collaboration tools or host filesystem routes are disabled. These need actual negative tests before real material is sent.

The current Comet path produces/guards original actions and accepts outcomes; it does not launch any of these CLIs. The existing consensus adapter has bounded read-only Claude/Codex/ZCode launch logic, but it is not a general provider: it contains provider-specific credential/config handling and its old material authorization is consumed. Do not execute its auth extraction or embed its review loop as another controller. This intake read only its code.

Current chat tools such as exec_command/Node REPL are harness capabilities, not a product-registered Comet transport. They are not automatically callable or qualified by this delivery profile.

## What SourceReader must actually establish

1. `clientProcessId` currently means the **Docker attach client PID**, not the in-container method PID. `clientExitCode` is that client's exit. The fixed Docker engine's inspected container terminal is a separate fact. Equality alone permits7==7; it does not mean success. This worker did not rerun the Core owner's reported wrapper-exit7 or launchId-replacement cases; static source confirms why a producer must carry stronger facts.
2. A successful required check needs its actual registered command/process terminal and exit0, plus valid container termination where applicable. A wrapper can exit0 while an inner command exits7; a worker can emit pass JSON and exit7. Both must be rejected. Unknown, signalled, restarted, OOM/error, mismatched, truncated or missing observations cannot become absence or pass. Model turn completed is also insufficient.
3. Source facts must be read by protected Host CODE from the fixed engine/strict handle and trusted harness/tool protocol, not from result JSON. Preserve separate engine/container identity, original start identity/time, host attach PID, actual tool process handles/exit, run/execution/attempt/epoch/revision, job/role/registration/binary digests and source qualification. Current inspect lacks some start/restart/OOM/error fields; any I02 extension belongs to its original owner.
4. Original launchId/handle must be frozen in the original pending execution record and matched thereafter. Reattaching with a new client PID must not mint a new launch. Missing original launch provenance or same-execution replacement remains UNVERIFIED. No worker-provided launchId or role selects the source.
