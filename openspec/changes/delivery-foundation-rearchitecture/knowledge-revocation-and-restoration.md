# 已发布知识的授权失效、访问隔离与恢复

日期：2026-10-19。状态：Grill 设计，尚未实施。

## 0. 范围与关键区分

G13 已确认：首版自动发布仅覆盖登记、权限可核验的项目资料域与专用受管 Outline 文集。Comet 在固定受管 Runner 是唯一业务主控，Matt 基础方法替代 Superpowers；技能迁移的实际证据与缺口见 matt-method-profile-migration.md。

“原发布回执不能再用于当前授权”与“原页面已经不能读取”是两个不同事实。标记 stale、停止 Agent 检索、unpublish/archive 或移位置都不能单独证明实际隔离。必须有资源端 ACL 约束和对应渠道读回。历史产品/规格交付不因后续知识权限变化被改写为从未完成。

## 1. 三类事件分开处理

| 事件 | 失效与即时限制 | 后续处理 |
| --- | --- | --- |
| 源许可撤销/缩小 | 当前 source→知识授权判定失效；暂停受影响自动读取、引用、发布和相关在途接纳 | 获取当前有效权限，查影响闭包；若目标不再合法则隔离 |
| 目标增加读者/分享/公开入口 | 当前有效受众证明失效；停止继续向该范围发布，受控检索先禁入 | 收窄分享/权限或隔离到预先批准空间，验证原读者/新未授权受众不能读 |
| 预授权过期/撤销 | 依其语义停止相应动作，不能自动续期 | 区分发布操作权与内容持续披露许可，获取新合法授权或维持隔离 |

预授权需要明确 publish_until（新发布/更新可执行到何时）和 content_use_until（已发布内容的持续披露许可期限/条件）。仅发布权过期不自动等于过去合法内容必须撤回；持续披露许可到期则不能继续提供内容。未写明持续使用语义的 grant 不走自动发布，不默认永久有效。源权限撤销始终触发当前披露条件重算，不能以未到期旧 grant 覆盖。

连接器凭据过期与资料许可撤销也不是同一件事；前者造成当前权限未知，按已冻结的 fail-closed/新鲜度规则处理，不能把 API 错误当公开或自动认定权限恢复。

## 2. 谁发现、谁决策、谁执行

| 角色 | 职责 | 禁止 |
| --- | --- | --- |
| Webhook/授权到期 tick/周期核验采集器 | 验证事件来源，登记事实与资源 ID，补查最新权限；只提交事件给 Comet | 不自行改 ACL、恢复内容或维护业务阶段 |
| Comet | 找影响闭包，登记唯一维护 operation，失效回执/暂停派发，决定允许的隔离/恢复动作和重试 | 不以 hook mode、Agent 自报或未验证旧 ACL 判定安全 |
| 受控隔离执行器 | 按单独预授权的受管对象执行收窄访问、撤 share/成员、必要迁入隔离域等动作 | 不持内容发布/签发根权限，不任意删除或扩大对象范围 |
| 独立授权/访问验证器 | 读实际源/目标权限、负向访问与渠道结果，给出可审计回执 | 不自改内容后自评已安全 |
| 源/目标 owner 或有效委托人 | 签发新授权、处理超范围/冲突/隔离失败与风险决定 | 无对应权力的人不能通用接受风险代签 |

普通 Publisher 的 publish grant 不包含改 ACL 的权力，因此需事先由有权 owner 单独批准隔离能力：仅针对受管实例/条目/文集、仅收窄访问或移到指定隔离域、不删除、不可顺手恢复/扩权。不能从“允许发布”自动推导“允许改权限”。未取得该能力前，不能承诺自动隔离已实现。

## 3. 影响闭包与同一主控

维护关联：source ID/revision → 候选/审查 → LLMWiki 条目 → Outline document/revision → 派生条目/附件/缓存/索引/消费回执。采用真实输入来源，不只追最后展示的引用；多来源知识受任一失效来源影响。不能证明影响边界时，对该受管域保守暂停，不能遗漏部分页面后报全量完成。

- 原交付 Run 仍未完成：在同 Run 处理/等待，失效的 K 回执阻断收尾。
- 原交付 Run 已 completed：保留其历史；由 Comet 接受当前权限事件，启动关联原发布回执的权限维护 Run/作业。不是重开已归档产品需求，也不新造巡检 controller。
- Classic 当前没有被验证具备知识维护类型；如需新的轻量维护入口，应复用 Comet Run/事务/continuation 引擎并显式扩展，不能强装一套外部状态机，或把维护硬塞成新的完整 OpenSpec 产品变更。
- 定时器/CI 只提供到期/核验事实，调度与动作领取仍由 Comet 负责；权限平台执行其资源 ACL，不是第二交付主控。

维护 key 绑定逻辑知识 ID、当前源/目标授权指纹、grant 生命周期与 policy；重复/乱序事件先对照可信当前事实，恢复原 operation。维护 epoch 防旧结果接纳，撤销优先于旧恢复；同对象不并行执行相互冲突的发布/权限写入。

## 4. 隔离的执行与判定

1. Comet 登记受影响对象与新授权代际，停止相关受管读取/引用和发布接纳，取消或冻结已读取失效资料的在途执行；历史上下文无法被“收回”，需记录可能暴露范围。
2. 取得真实源/目标现状，对“实际不可访问”而非仅状态标签制定预授权的最小收窄动作。
3. 隔离执行器调用所选部署实际支持的权限接口。可能涉及撤公开 share、收窄显式用户/组、处理继承或移到批准隔离文集；单一动作的语义不能假定。
4. 独立核验实际访问：受控 MCP/RAG、Outline 直接链接、搜索/摘要、父子树/单页/public share、附件/预览等 required 渠道。管理员仍能读到只证明对象存在，不能证明其他人不能读。
5. 全部必需路径已约束、无未调和权限写入时才记录 isolated；否则保持 isolating/unknown、告警 owner 并继续同一 operation，不伪报已隔离。

Outline 集合/父级继承与单页分享叠加，移到私有文集可能仍需处理已有分享，unpublish/archive 不等于所有路径都撤权。附件旧 URL、导出、浏览器缓存、已复制内容不能承诺即时收回；是否纳入可阻断范围需明确。保留必要审计原件也必须在授权受限存储，不能把正文继续留在普通 CI 日志。

当前官方 API 有 shares.revoke、documents.remove_user/remove_group/move/unpublish/archive 等入口；这仅证明操作面存在，不证明隔离语义或跨步骤原子性。尤其 lastRevision 主要是内容更新并发条件，不能当 ACL 写入 fencing。没有权限 CAS 时，受管单写者/收窄外部改权与后验核验的局限必须实测；旧在途恢复可能成功时不能提前宣布 isolated。

## 5. 恢复必须重新证明

恢复前：源 owner/委托和 grant 当前有效、持续披露许可成立、来源内容/权限完整、目标有效受众落在允许交集、独立审核/检查通过。首版对恢复重新做当前授权与知识审核，不只撤 stale 标签。

根据最新有效范围生成恢复计划，不原样回放旧 ACL 快照；已离组/撤权的人不能被重新加回。Runtime 记录新的 epoch/operation 后再执行允许恢复，独立读回所有 required 渠道，才变 active。内容/需求/设计改变时仍按 R09 对相关完整下游重新验，不拼接旧审查票/批准。

旧恢复回调、迟到 publish 成功或乱序权限事件不能覆盖较新的隔离代际。已经发出的网络请求不能靠本地 epoch 收回，必须调和实际结果；结果未知时保持阻断。隔离 API 不可用则立即停止本系统消费/新发布，但不能称 Outline 全面不可读，应记录暴露未消除、告警并请求有权 owner 应急处理。

## 6. 状态是证据投影，不是第二套主控

建议展示：needs-revalidation / isolating / isolated / restoring / active / retired，并附实际访问证据和未覆盖渠道。这是知识对象安全视图，执行的 current-step/owner/attempt、重试、等待和恢复仍只有 Comet。

老发布回执保留为“当时该版本和受众下成立”，不继续支撑当前消费；原产品完成历史不被反复复活。新的维护结果形成新的权限/访问回执并更新检索可用性。

## 7. 最小改动与必须实证

在既有 Comet 接入点扩展：可信权限事件输入/索引、source→产物影响查找、共同授权 gate、维护动作与 continuation、唯一 operation/epoch 及隔离/恢复适配、独立访问验证与状态展示。RunStore/锁/事务仍复用；不让 Ponytail 或监听器签发授权、写 ACL 或启动独立重试循环。

故障测试至少覆盖：源撤销/目标分享扩大/许可到期、两种期限区别、多源派生传播、标记失效但网页仍可读、继承/附件/搜索漏隔离、重复乱序事件、隔离中断/失败、旧恢复回调、权限恢复不重新加回离组成员、完成后的维护不重写产品历史。原生支持与实际部署隔离结果分别报告。

## 8. G14/G15 已确认；时限需准入实证

用户已选择 G14 A 与 G15 A：正常依赖下以 5 分钟完成资源端隔离及独立读回为目标；故障时独立告警、原实例恢复补偿与人工应急，接受可能超时但必须记录暴露窗口及违约。下表是该目标的推荐预算与运维配置，不是已通过实测的保证；细分预算和运维参数须经容量/故障实证冻结。登记规模、分页、限流、源权限传播与所有 required 访问渠道必须在准入时证明满足预算，否则该资料域不能启用此自动发布配置。

| 环节 | 推荐时限与起算点 | 责任与越限处理 |
| --- | --- | --- |
| 事件快路径 | 健康条件下，可信事件到达入口后 30 秒内持久登记 | 入口先持久化再确认；重复输入提交给同一 Comet operation，不能代替全量核验 |
| 周期兜底 | 每 1 分钟发起一轮完整登记范围核验，每轮最多 1 分钟 | 采集器只交事实；Comet 领取/接纳核验动作。必须证明每个登记资源覆盖，不能只查增量事件 |
| 撤权检测 | 从源/目标实际权限变化到 Comet 持久接纳，最多 3 分钟 | 预算：源查询可见延迟 ≤1 分钟＋等待下轮 ≤1 分钟＋完整扫描 ≤1 分钟；不是从收到通知才起算 |
| 访问隔离 | 检测接纳后 2 分钟内完成收窄和独立读回，正常条件端到端最多 5 分钟 | 包括队列、API、重试、访问传播和所有 required 渠道验证；首次调用失败即告警，不等待预算耗尽 |
| Runner 故障检测 | 心跳每 30 秒；独立监控每 30 秒检查，心跳年龄 >90 秒告警，最迟 2 分钟发现 | 监控必须在 Runner 故障域外；同时监测完整扫描水位，心跳正常但超过 2 分钟无完整扫描也告警 |
| 故障告警送达 | 监控判定或隔离首次失败后 30 秒内送达已登记渠道 | 独立告警系统投递/重投并升级；渠道不可达走备用渠道，告警未送达不能记已响应 |
| 运维恢复 | 建议故障检测起 10 分钟内恢复原 Comet 实例并开始对账 | 属恢复目标，不是宕机期间 5 分钟隔离保证，也不代表恢复开始即完成补偿 |

上述正常条件要求 Runner/持久存储、源/目标权限 API、访问传播和独立核验可用且容量达标。未知源更新时间、无界权限传播、未覆盖分页或限流超预算时，不能报 3/5 分钟达标。已知 content_use_until 应提前安排隔离以不越过期限，不把周期检测预算当作可继续披露的宽限期。预定隔离无法完成时提前告警，不能到期自动续权。

单 Runner 宕机、网络分区或 Outline 权限接口不可用时，事件＋轮询不能提供固定墙钟隔离上界。系统应如实记录风险窗口和时限违约，不能暂停计时后继续报达标。外部监控只能发现/告警，既有直接网页入口可能仍可读；若要求故障下也有硬隔离上界，需要另议资源端到期拒绝访问/统一授权入口等能力，不能由监听器暗中接管 Comet。

## 9. 告警、重试和应急的权责

- Comet 是唯一业务动作所有者：保存事件、维护 operation、attempt、next_attempt_at、授权代际、结果未知标记与 continuation。安全维护动作优先于新发布；不让长时间 Builder 占用使权限核验超时，容量/优先级也需负载验收。
- 独立监控/告警系统只读取心跳、完整扫描水位、未完成隔离和截止时间，向登记的平台值班与知识权限值班告警；只保存告警投递/升级状态，不维护业务阶段、不派发 Agent、不写 ACL。监控不可用也必须由既有平台监控发现，不能只让 Comet 自报健康。
- 进程监督器只在原 Runner 上重启同一 Comet 服务；建议 5 分钟内最多 3 次，失败升级平台值班。不能复制状态到成员机器继续、启动第二业务 owner；旧进程未确认终止或存储归属不明时不并发恢复写入。
- 隔离失败首次即发事件给独立告警系统；Comet 在 2 分钟隔离预算内最多 3 次尝试，先调和未知结果再重试。权限拒绝/凭据撤销交有权人，不盲目重试；429 遵守 Retry-After，不能满足截止时间则记录违约并升级。超出快速预算后进入同一 operation 的低频恢复重试（建议每 5 分钟，持续告警不解除），终止/超范围动作必须由有权人决定；不会由 hook 或执行器自行开循环。
- 平台值班处理 Runner、网络与存储；知识权限值班协调源/目标 owner 做资源端应急封禁。建议主值班 5 分钟未确认升级备用值班。姓名、备用人、渠道与隔离操作授权都须先登记，否则不能启用无人值守发布。
- 应急人工只能凭自身资源权限/单独应急授权做收窄，不能借普通发布凭据扩权；操作审计回送 Comet，不能改 Comet 阶段或伪造回执。独立核验后由 Comet 接纳结果。资源管理员紧急封禁不是第二业务调度器。

## 10. 宕机恢复与漏报补偿

1. 监督器恢复原实例；Comet 先恢复持久事务、唯一 owner 和未完成 operation，冻结新发布/自动恢复，不能只见 archived 或旧绿灯就完成。
2. 调和所有已发出但结果未知的远端操作，读取真实对象、分享和 ACL。新 epoch 只拒绝旧回执，不会撤回已发出的 HTTP 写；旧恢复可能扩权时继续保持风险未闭合。
3. 不依赖可能漏报的事件游标，对全部登记源/目标及实际发布对象做完整快照对账。检查删除、分享扩大、grant 到期、派生条目、附件与孤儿对象；权限错误/分页不完整/来源映射缺失均视为未知，保守暂停受管域并升级。
4. 差异由 Comet 登记为幂等维护动作；撤权/隔离优先，使用当前真实权限，重复通知不重开业务流程。先完成相应隔离与独立读回，再允许当前授权下的新发布/恢复；域可分批解除暂停，未核验域保持暂停。
5. 分开保存事件持久接收游标、完整核验水位、资源端隔离回执。接收成功不代表处理完，扫描完整不代表隔离成功；失败对象不能被一次成功扫描清掉。
6. 补偿完成要包含受影响对象分母、未完成列表、风险起止时间与时限违约。事故关闭不抹掉违约；已下载/复制内容的暴露另行记录，不声称恢复后可以追回。

固定单 Runner 的进程崩溃恢复、主机永久损坏、持久存储丢失是不同故障。后两者依赖另行证明的备份/受控迁移流程，不把 10 分钟目标当作已具备的能力。迁移仍必须先隔离旧写者并保持一个 Comet 权威。

G15 已确认 A：采用正常依赖下 5 分钟隔离目标与故障告警/恢复/人工应急，不要求本期故障期间自动硬隔离上界。接受超时不等于授权继续披露或免除响应；保留暴露窗口、违约和应急记录。后续若要求故障下硬上界，须重新评审资源端访问控制范围，不以增加监听器主控解决。
