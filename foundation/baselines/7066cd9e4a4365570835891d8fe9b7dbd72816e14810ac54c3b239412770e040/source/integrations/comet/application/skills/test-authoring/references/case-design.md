# Case design

从 test basis 提取“条件/规则/状态/角色/边界/效应”，再生成测试。实现能说明接缝与当前行为，不能批准预期。缺规则不通过默认值补齐；已批准规范优先，冲突保留 unresolved。

| 形状 | 技术 | 输出检查 |
|---|---|---|
| 有序范围、金额、长度、时间 | 等价类 + BVA | 合法域、非法域、min-1/min/min+1、max-1/max/max+1；整数/小数单位按规范 |
| 多条件共同决定结果 | 决策表 | 条件组合、动作与不可达组合依据；不能只测每个条件单独成立 |
| 当前状态影响事件合法性 | 状态迁移 | 有效/无效迁移、guard边界、终态与重复事件 |
| 多参数环境组合 | 风险优先 + pairwise | 必测高风险组合先保留；写明缩减覆盖和未测组合，不称穷举 |
| 一串真实用户动作 | 场景/路径图 | happy、相关拒绝、失败恢复及终态 authority；跨边界每条关键 edge |
| 可表达不变量/代数关系 | 属性测试 | 有意义性质、生成策略、反例与收缩；没有性质则用例测试更合适 |

最少用例字段见 templates/case.json。一个用例可以验证多个有关联的断言，但应清楚是哪条规则失败；非法输入尽量每次只改变一个关键条件，避免先触发另一个校验而掩盖目标边界。

边界示例：订单total>=100免运费、否则8，会员免运费。先列普通/会员×金额区间的决策规则，再测99.99/100/100.01及合法最小值。不要将“当前实现total>100”写成预期；规范边界100应能使错误实现失败。

优先测风险/变更路径，不用行覆盖率替代需求覆盖。对未决预期列出具体问题、影响的需求ID和可继续设计的部分。用户拒绝提问不授权编造业务规则。
